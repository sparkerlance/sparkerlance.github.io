Defold 插件研究 系列目錄

研究目的

建立架構清晰、權責分明的開發框架，
確保專案可擴展、易於閱讀，並方便後續添加或修改功能。

簡介

Defold

Defold 是一個輕量級 2D / 3D 遊戲引擎，適合快速開發遊戲。
官方網站：https://defold.com

Insality

Insality 是提供了一系列插件的作者，例如 Event、Decore、Druid 等。
GitHub：https://github.com/Insality

系列概述

目標讀者

  • 已掌握基本 Lua 與 Defold 開發流程的遊戲開發者
  • 對 ECS 架構、插件應用與專案設計有興趣的開發者
  • 希望建立可維護、可擴展遊戲專案架構的開發者

內容概述

  • 系列文章逐個介紹 Insality 的 Defold 插件
    （Event、Decore、Druid、Panthera、Saver、Quest、Detiled、Lang）
  • 每個插件包含：研究目標、Checklist、最小實驗、使用建議與架構設計

章節目標

  • 理解各插件用途與設計理念，避免僅照抄範例
  • 學會在實際專案中解耦系統與 UI、動畫、存檔、任務等
  • 掌握 ECS 架構與事件驅動的最佳實踐，提高專案可維護性

完成收穫

  • 建立專案架構清晰、權責分明、可擴展的 Defold 專案
  • 清楚掌握每個插件使用時機與與其他系統整合方式
  • 能快速搭建測試小專案驗證功能，方便未來擴展與修改

Insality 插件一覽

連結 插件名稱 簡短說明

關於Insality插件建議的研究順序

Event → Decore → Druid → Panthera → Saver → Quest → Lang → Detiled(視需求)

每篇文章包含：

  • 研究目標
  • Checklist（必做項目）
  • 不建議做的事項
  • 最小實驗（Hands-on demo）
  • 開發前與階段性確認事項

1. Event（跨 Context 事件系統）

研究目標
取代 msg.post 做邏輯層事件，解耦 System / UI / Animation

Checklist

  • 建立 global event bus
  • System 訂閱事件
  • UI 發送事件（例如 button click）
  • Animation event → Event
  • 確認 event scope（local / global）

不建議

  • 用 Event 傳高頻資料（每幀 position）

最小實驗

  • 按按鈕 → 發送 event → ECS System 接收 → 改變 entity 狀態

2. Decore（ECS 核心）

研究目標
純資料 Component，邏輯全在 System，熟悉 filter & entities cache

Checklist

  • 自己寫 3 個 component（只有 data）
  • 自己寫 3 個 system
  • 動態新增 / 移除 component
  • System filter 生效條件
  • 多個 system 同時作用在 entity
  • 不在 component 裡寫邏輯

最小實驗

  • Top-down 移動 + 撿道具 + 刪除 entity

3. Druid（UI 框架）

研究目標
UI 不直接碰 ECS，UI 只發事件 / 顯示資料

Checklist

  • 建立基本 UI screen
  • 使用 component（button / text）
  • UI → Event → ECS
  • ECS 資料 → UI 更新（透過 Event）
  • UI lifecycle（init / update / final）

不建議

  • UI 直接操作 entity

最小實驗

  • HP 改變 → 發 event → UI 血條更新

4. Panthera 2.0（動畫狀態機）

研究目標
動畫 = 狀態，動畫事件 = Gameplay 觸發點

Checklist

  • 建立 state machine
  • 切換 idle / move / attack
  • 使用 animation event
  • animation event → Event → ECS
  • ECS 狀態影響動畫

最小實驗

  • 攻擊動畫第 3 幀 → 產生 hitbox

5. Saver（存檔系統）

研究目標
ECS 資料序列化，解耦 Save / Load 與 Gameplay

Checklist

  • 儲存 player 狀態
  • 只存 component data
  • Load 後還原 entity
  • 處理版本變化（schema）

最小實驗

  • 關遊戲 → 再開 → player position 還原

6. Quest（任務系統）

研究目標
任務 = 狀態機 + 事件驅動

Checklist

  • 定義 quest flow
  • Event 觸發任務進度
  • Quest 完成發事件
  • Quest 與 ECS 解耦

最小實驗

  • 撿 3 個道具 → 任務完成

7. Detiled（Tiled → ECS）

研究目標
地圖 = 資料，地圖生成 entity

Checklist

  • 從 Tiled 讀資料
  • Object layer → ECS entity
  • 自動加 component
  • 和 Decore system 協作

最小實驗

  • Tiled 放敵人 → 遊戲自動生成

8. Lang（Defold Localization / 語言插件）

研究目標
管理遊戲多語系文本，簡化 UI 與 ECS 顯示文字的綁定

Checklist

  • 建立語言檔（JSON / Lua table）
  • 定義 key → text 映射
  • 文字更新自動刷新 UI
  • 多語系切換測試
  • 與 Event 系統結合（語言切換事件）

不建議

  • 將業務邏輯綁定在語言檔

最小實驗

  • 切換語言 → UI text 自動更新

開發前與階段性確認事項（系列共通）

開發前確認事項

開始研究或使用每個插件前，可評估以下事項：

  • 插件是否必要，缺少它會失去哪些功能
  • 插件的責任層是否清楚，與其他系統是否解耦
  • 插件的使用範圍與限制是否清楚

階段性確認事項

完成插件研究或小專案後，可確認以下項目：

  • 功能是否符合預期
  • 是否按照 ECS / Event / 系統架構保持權責分明
  • 是否容易擴展或修改
  • 是否有明確的測試或最小實驗驗證

建議總控 Repo

完成 2–3 個插件研究後，可建立 repo：

/architecture_lab
├─ ecs_basic
├─ ecs_event
├─ ecs_ui
├─ ecs_animation
└─ ecs_save

每個資料夾對應一個可執行的小專案，用於實驗與驗收。
這些小專案可用來實際操作插件功能、檢驗 Checklist 項目是否正確運作，
熟悉各系統之間的互動與解耦方式，完成後可直接應用於大型專案。

完整列表上實作後，將得到什麼？

  • 從 「學習插件怎麼用」
  • 到 「打造專案骨架」

能建立一套 架構清楚、責任分明、可長期維護的 Defold 專案骨架。

核心能力包括：

  • 插件整合與理解
    理解每個插件在整體架構中的位置、責任與邊界，而不僅僅是使用範例。

  • 功能與系統判斷（MVC / MVCS / MVVM 對應）
    開發新功能時，可依照架構分層判斷放置位置：

- Presentation 層（View / ViewController）

  • 負責接收使用者輸入
  • 顯示畫面與狀態
  • 可以調用命令 (Command)
  • 可以訂閱/監聽事件 (Event)
  • 不直接自行改變 Model

- System 層

  • 負責共用邏輯處理（如計時、商城、任務系統等）
  • 接收事件並執行邏輯
  • 發送事件通知其他層

- Data 層（Model）

  • 定義資料結構
  • 提供 CRUD 行為
  • 透過事件告知資料變更

- Utility 層

  • 提供基礎設施（儲存、序列化、網路等）
  • 不處理遊戲邏輯

明確規範：

  • 上層可以直接調用下層，但下層不直接依賴上層
  • State 改變後的通知必須用事件
  • 改變狀態必須用 Command

- 事件與指令（Command / Event）

這是架構核心，用來實現解耦與流程分離：

  • Command

    • 代表「要做什麼」的操作指令（不可有狀態）
    • 由上層（例如 View / Controller）發出
    • 系統 / Model 在收到 Command 後進行行為改變
    • Command 本身可以再觸發 Event

  • Event

    • 代表「事情已經發生」
    • 由 Model / System 發出
    • 可由 Presentation、System、Model 層訂閱
    • 用於狀態通知與跨層溝通

這樣的設計可以達成：

  • 操作與狀態分離（CQRS 思維）
  • 改變狀態必須用 Command（避免直接呼叫改資料）
  • 狀態改變後通知所有訂閱者（Event 機制）

📌 用一句話總結 

Command 負責下達意圖，Event 負責廣播已完成的狀態改變；  
上層發送 Command，底層接收 Event；  
Model/Logic 與 UI 之間透過事件溝通，而不直接耦合。

  • 最小實驗驗證
    先做 mini project 驗證設計，再回到主專案延伸功能，保持專案穩定性。

  • 維護與擴展能力
    對於新增玩法、重構系統或接手舊專案，能快速定位問題，而不增加額外風險。

這系列筆記，目標是記錄 從單功能實作 到 專案架構設計 的完整過程。

在過程中將一個個完成列表上的小專案，然後在每個後續專案復用之前的成果，
並在架構之上持續優化。

讓我們一起走上可維護、可擴展的 Defold 遊戲開發之路。
