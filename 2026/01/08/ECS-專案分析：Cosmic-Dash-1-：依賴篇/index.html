ECS 專案分析：Cosmic Dash (1)：依賴篇

0. 下載或Clone專案

Cosmic Dash : https://github.com/Insality/cosmic-dash-jam-2025
下載後使用 Defold 打開專案並資料夾選擇 game.project。
這裡我選擇使用 Fork 這個軟體來做版本管理，所以我的操作是：

  1. 複製 GitHub URL
  2. File > Clone
  3. 選擇路徑，例如 D://Defold/

成功下載後，你會在 D://Defold/ 看到名為 cosmic-dash-jam-2025 的資料夾。

1. 查看 game.project 中的專案設定 (Project)

  1. 使用 Defold 開啟專案後，左側會有一個 Assets 視窗。
  2. 在 Assets 視窗中向下捲動，找到綠色圖示的 game.project 檔案。
  3. 雙擊 game.project 開啟它。
  4. 點擊”中上視窗”左側的 Project 分頁，即可看到專案設定 general project settings。

  • 這行欄位中使用逗號 , 分隔多個資料夾
  • /locales 包含多語系 JSON
  • /tiled/export 包含 Tiled 地圖 JSON

2. 查看 game.project 中的專案入口 (Bootstrap)

  • Main Collection：/loader.collection → 專案啟動時會載入的起始場景
  • Render：/builtins/render/default.render → 預設渲染設定（包含相機、解析度等）

loader.script 整體結構與作用

loader.script 是專案的入口腳本，

附加在 /loader.collection 上。它的主要任務是：

  1. 初始化隨機種子
  2. 設定各模組的 Logger
  3. 初始化 Druid UI 框架
  4. 設定視窗事件監聽
  5. 初始化存檔系統 (Saver)
  6. 初始化多語言系統 (Lang)
  7. 載入 Tiled 導出的地圖資源
  8. 發送 start_game 訊息，觸發後續遊戲載入

在 on_message 中收到 start_game 後：

向集合中 ID 為 game_proxy 的遊戲物件發送 "load" 訊息。

#game_proxy 是 /loader.collection 中的一個 proxy 物件，用來非同步載入主要的遊戲場景。
"load" 訊息會觸發 proxy 開始載入真正的遊戲 collection（極有可能就是包含 Panthera ECS 的 world 與所有 systems 的主場景）。

當 proxy 載入完成後，Defold 引擎會自動向原本的發送者（即 loader）回傳 "proxy_loaded" 訊息。
loader 收到 "proxy_loaded" 後，會執行以下三行：

  • "init" → 呼叫載入完成之 collection 中所有 game object 的 init() 函式
  • "enable" → 啟用所有 component，讓 update()、fixed_update() 等開始被呼叫
  • "acquire_input_focus" → 讓新載入的場景取得輸入焦點（鍵盤、觸控等）

這整段流程正是 Defold 官方推薦的「啟動畫面 + 非同步載入主遊戲」模式，在大中型專案中非常常見，能有效提升載入體驗。

推論：Panthera ECS 何時開始運作？

根據上述流程，我們可以合理推斷：

  • Panthera ECS 的 world 以及所有 systems 都位於被 game_proxy 載入的那個主 collection 中。
  • 只有在收到 "proxy_loaded" 並發送 "init" 與 "enable" 之後，Panthera 的 systems 才會正式開始執行 update(dt) 等邏輯。

這樣的設計確保了所有前置資源（多語言、存檔、Druid UI 風格、Tiled 地圖資料等）都已完整初始化，才進入真正的遊戲邏輯，避免潛在的空指標或資源未就緒問題。

小結

loader.script 的設計極為清晰且模組化：

  1. 先完成所有全域系統的初始化
  2. 再觸發主遊戲場景的非同步載入
  3. 載入完成後才正式啟動 ECS 與遊戲邏輯

這種分階段啟動方式，能有效避免載入期間的畫面卡頓，並嚴格保證依賴關係的正確性。
