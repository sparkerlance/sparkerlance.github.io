什麼是 API？

簡單來說，API 像是「語法」。


不只是在前後端之間，任何套件或框架，只要要給別人使用，都一定會有 API。
前端與後端溝通時，後端通常會提供一份 API 使用說明，告訴前端在什麼情況下該呼叫哪一個 API，以及會回傳哪些資料。
在遊戲公司時，像是排行榜系統，前端只要呼叫對應的 API，後端就會回傳玩家的通關時間、排名、人數，或是累積遊玩時間等資料；
又或者在遊戲啟動時，前端會呼叫「啟動驗證」的 API，只要驗證通過，後端就會回傳可以進入遊戲的結果。
前端不需要知道後端怎麼計算排名、怎麼驗證帳號，
只要依照 API 的規則呼叫，就能拿到對應的結果。
同樣的概念，也會出現在使用各種套件或框架、遊戲影擎時。

舉例來說，當我在學習 ECS（Entity Component System）時，在專案裡看到了一個檔案：

[API.md]

沒有使用過套件或框架的開發者會冒出一個疑問：

  • 什麼是 API？

一、API 的白話文解釋

API =「我可以怎麼用這個東西」

API（Application Programming Interface）
簡單來說就是：
「這個程式／套件提供了哪些功能？我要怎麼呼叫它？」

你可以把 API 想成一個函式列表。
正確的呼叫，就會給你預期的結果。

用生活例子比喻

想像你有一台飲料機：

  • 按鈕 A：可樂
  • 按鈕 B：紅茶
  • 按鈕 C：綠茶

你不需要知道飲料機裡面怎麼運作
你只需要知道：

  • 按哪個按鈕
  • 會得到什麼結果

這些「按鈕」就是 API

二、在程式世界裡 API 是什麼？

在程式中，API 通常是：

  • 函式（function）
  • 模組（module）
  • 方法（method）
  • 可以呼叫的介面

舉一個簡單 Lua 例子

這些就是 ECS 套件提供的 API
你只要知道：

有哪些函式
要傳什麼參數
會回傳什麼

不用知道 ECS 內部怎麼實作。

三、為什麼 ECS 套件一定會有 API？

ECS 本身是一種「架構思想」，但實際使用時：

每個 ECS 套件實作方式不同
每個套件提供的功能也不同

所以作者一定要告訴你：
「我這個 ECS，你可以這樣用」
這就是 API 文件 的用途。

四、API.md 是什麼？

API.md = API 說明文件
當你在插件（例如你看到的 decore）裡看到：
textAPI.md
通常代表：

這不是教你 ECS 理論
而是告訴你「有哪些函式可以用」

內容通常會像這樣：
text## ecs.create_entity()
建立一個新的 entity

Returns

entity id
這就是 API 文件的典型格式。

五、API 跟教學（Tutorial）的差別

這是很多新手最容易混淆的地方。

教學（Tutorial）

原理+範例
告訴你「為什麼要這樣做」
有流程、有例子
適合初學概念

API 文件（API.md）

使用說明書
告訴你「你可以呼叫什麼」
API 是查資料用的，像是「如何使用的字典」

六、哪時 去看 API

學新框架時，通常的流程是：

  1. 先懂概念

    • Entity 是什麼
    • Component 是什麼
    • System 在做什麼

  2. 再來才是看 API

    • entity 要怎麼建立？
    • component 要怎麼加？
    • system 要怎麼註冊？

七、應該怎麼看 API.md？

學「新框架」的建議：

第一次看

不用全懂，只要知道：

  • 有哪些主要功能
  • 大概能做什麼

實作時

當你想做某件事時，例如：

  • 「我要幫 entity 加 component」

再回來查 API.md
找相關函式

八、簡短總結

一句話記住 API 是什麼：

API 是一組「對外公開、如何使用的函式與介面」

而 API.md 是在說明這些函式怎麼用的文件
