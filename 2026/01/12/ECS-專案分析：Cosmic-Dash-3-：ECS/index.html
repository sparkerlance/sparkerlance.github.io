2. game.script 與 ECS world 的建立

game.script的核心作用如下：

  • 建立 ECS world，並將 systems.get_systems() 回傳的所有系統加入 world
  • 註冊所有遊戲 entities（玩家、敵人、道具等）到 world，分組為 "game"
  • 註冊後 ECS world 才能在每幀 update 循環中管理 entities，並讓各系統執行邏輯與視覺更新

簡單理解：ECS world 是教室，systems 是老師，entities 是學生。這行程式碼把所有學生帶進教室，老師才能開始教課。

遊戲流程

  • update(dt) → 驅動 ECS world 每幀更新所有 systems
  • on_input() → 將玩家輸入交由 ECS world input system 處理
  • final() → 卸載 ECS world 與 entities 資源

3. Cosmic Dash 的 架構

在理解 game.script 的 ECS 啟動流程後，再回頭觀察 Cosmic Dash 的專案結構，可以更清楚看出作者實際如何在 Defold 中落實 ECS 架構。

值得注意的是，Cosmic Dash 並非完全資料驅動（data-driven） 的 ECS 實作，而是結合 Defold 原生的 collection 樹狀結構，以 collection 作為場景與物件的組織方式，再將其註冊進 ECS world。

整體啟動脈絡如下：

loader.collection
  └─ game_proxy → 載入 game.collection
        └─ game.script → 建立 ECS world

也就是：

loader.script 掛載於 loader.collection

game_proxy 是 loader.collection 的子物件，負責載入 game.collection

game.script 掛載於 game.collection，作為 ECS world 的實際入口

從這個結構可以觀察到一個關鍵設計特徵：

遊戲中實際會用到的 game object，都已經作為 game.collection的子物件存在於場景當中

這代表 Cosmic Dash 並不是在執行期間大量動態生成物件，而是：

  • 以 game.collection 中的 子物件 GO 作為模板

  • 在 ECS world 初始化時註冊完整的 entity 清單

  • 在遊戲運行期間，透過 啟用 / 停用 / 複製 的方式來操作 entity

這樣的設計有兩個好處：

  • 方便將模板物件直接註冊進 ECS 系統

  • 符合 Defold 原生工作流程，降低工具與資料轉換成本

  • 配合 Druid 與動畫系統（如 Panthera）的使用方式，物件需先存在於場景中才能進行 bind

4. 小結

到此為止，我們已經完整分析了 game.script 的主要流程：

  1. 建立 ECS world
  2. 註冊 entities
  3. 初始化 GUI 與 Debug Panel
  4. 每幀更新循環

這種集中管理的方式體現了 ECS 的結構與優勢：

  • ECS 結構：將遊戲邏輯拆成 entities（數據）、components（屬性）、systems（行為）三層，數據與邏輯分離
  • 集中管理：ECS world 統一管理所有 entities 和 components，systems 在 update 循環中依序運行
  • 效能優勢：統一 update 減少內存碎片化，提高 CPU cache 命中率，遊戲邏輯運行更高效
  • game_proxy + game.collection 展示了 Defold ECS 的標準遊戲啟動架構
  • 分階段啟動：全域系統 → proxy 載入 → ECS world 建立 → 遊戲邏輯循環

綜合以上分析，可以將 Cosmic Dash 的 ECS 架構理解為一種：

Logic-driven ECS + Scene-driven presentation

  • ECS world：負責「誰動、怎麼動、什麼時候動」
  • Defold Collection / GO / GUI：負責「長什麼樣子、如何被綁定與呈現」
這種混合模型在 Defold 生態中相當成熟，在維持 ECS 架構的同時，
充分利用 Defold 原生工具（Collection、GUI、動畫系統）的優勢。
